# مفرّغ الوقّاد

خدمة Flask واحدة تجمع بين:

- **مفرّغ الوقّاد**: تفريغ الملفات الصوتية والمرئية إلى نص عربي.
  - المحرك الأساسي: Cohere.
  - المحرك الاحتياطي: Deepgram عند تعذر Cohere.
  - تنقية النص إملائياً: Gemini.
- **الورّاق**: بوت تيليجرام لأرشفة الملفات + واجهة Mini App.

## المتطلبات

- Python 3.12
- ffmpeg (مثبت داخل Docker)
- قاعدة بيانات PostgreSQL
- مفاتيح API من Cohere و Deepgram و Gemini
- توكن بوت تيليجرام

## التشغيل محلياً

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# املأ القيم داخل .env
export $(grep -v '^#' .env | xargs)
python app.py
```

الخدمة تعمل على `http://localhost:10000`.

## النشر

المشروع مهيأ للنشر على Render عبر `Dockerfile`:

- المنفذ: `10000`
- فحص الصحة: `/health`
- يعمل بمستخدم غير جذري.

## أسرار الويبهوك

عند ضبط `TELEGRAM_WEBHOOK_SECRET` و`WARRAQ_WEBHOOK_SECRET` تصبح طلبات الويبهوك مرفوضة (403) ما لم تحمل الترويسة الصحيحة `X-Telegram-Bot-Api-Secret-Token`.

سجّل الويبهوك بالسر مرة واحدة (بعد النشر):

```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  -d "url=https://<BASE_URL>/telegram/transcriber" \
  -d "secret_token=<TELEGRAM_WEBHOOK_SECRET>" \
  -d 'allowed_updates=["message","callback_query"]'

curl -X POST "https://api.telegram.org/bot<WARRAQ_BOT_TOKEN>/setWebhook" \
  -d "url=https://<BASE_URL>/telegram/warraq" \
  -d "secret_token=<WARRAQ_WEBHOOK_SECRET>"
```

`allowed_updates` يجب أن يحتوي `callback_query`، وإلا فلن تصل ضغطات أزرار التصدير إلى الخادم أصلًا. عند الإقلاع يفحص التطبيق `getWebhookInfo` ويضيف `callback_query` تلقائيًا إن كانت القائمة مقيّدة بدونه، ويطبع النتيجة في السجل تحت `[WEBHOOK CHECK]`.

## التفريغ المباشر من المحادثة

أرسل ملفاً صوتياً أو فيديو إلى بوت مفرّغ الوقّاد في محادثة خاصة، وسيُفرّغ ويعود إليك في نفس المحادثة دون فتح أي صفحة.

- الملفات حتى `TRANSCRIBER_MAX_UPLOAD_MB` (20MB افتراضياً) تُنزّل عبر `getFile` وتُفرّغ مباشرة.
- ما يتجاوز الحد يردّ عليه البوت برسالة واضحة وزر يفتح صفحة الرفع، لأن حد تليجرام نفسه هو 20MB.
- المهام تدخل طابوراً بعدد عمال ثابت، فيرى المستخدم ترتيبه بدل أن يفشل طلبه بصمت عند الزحام.
- بعد النتيجة تظهر أزرار لتنزيل TXT أو DOCX، ولنسختي التدقيق لاحقاً.
- `/find كلمة` يبحث داخل **نص التفريغ كاملًا** لا في أسماء الملفات، بعد تطبيع عربي يتجاهل التشكيل والتطويل ويوحّد الهمزات (أ/إ/آ → ا) والتاء المربوطة (ة → ه)، ويزيل السوابق الشائعة (ال، وال، بال…). فكلمة «محاضرة» تجد «المحاضرة»، و«اصول» تجد «الأصول».
- `/find` وحده يعرض آخر تفريغات المستخدم، مع أزرار DOCX وTXT لكل نتيجة.

كل تفريغ يُحفظ في جدول `transcripts` ويُرسل ملفه النصي إلى قناة السجل إن كانت مضبوطة، مع بصمة مختصرة للمستخدم بدل معرّفه.

> ملاحظة نشر: الطابور داخل عملية Gunicorn الواحدة، لذلك يجب إبقاء `--workers 1` كما في `Dockerfile`. رفع عدد العمال يُنشئ طابوراً منفصلاً لكل عامل.

## تفريغ الروابط

يمكن إرسال رابط في محادثة البوت أو لصقه في صفحة الرفع، بدل رفع ملف:

- **يوتيوب**: يُنزَّل الصوت عبر `yt-dlp` ويُحوَّل إلى MP3 بجودة 64kbps قبل التفريغ.
- **رابط ملف مباشر**: ينتهي بـ `mp3` أو `m4a` أو `wav` أو `ogg` أو `opus` أو `mp4` أو `webm`، ويُفحص نوع المحتوى قبل التنزيل.
- الحد الافتراضي `TRANSCRIBER_URL_MAX_MB=150`. الرابط لا يمر عبر تليجرام، لذلك لا تنطبق عليه حدود 20MB.
- التنزيل يدخل الطابور نفسه، وتظهر مرحلة `downloading_url` في صفحة الرفع وتتبخّر رسالة الحالة كالمعتاد.
- الأمان: `http/https` فقط، ورفض `localhost` والشبكات الداخلية وفحص كل تحويل، لمنع استخدام الخادم للوصول إلى شبكة Render الداخلية.
- إذا طلب يوتيوب تحققًا من الخادم، أرسل ملف `cookies.txt` إلى البوت من حساب المطوّر؛ يُحفظ في قاعدة البيانات ويُستخدم تلقائيًا. `/cookies` يعرض الحالة، و`/cookies clear` يحذفه. بديلًا لذلك يدعم الخادم `YTDLP_COOKIES_FILE` أو `YTDLP_COOKIES_B64`.
- استخدم حسابًا مخصصًا لهذا الغرض، لأن الكوكيز تمنح وصولًا كاملًا للحساب. قد تمنع يوتيوب بعض عناوين الخوادم السحابية، وهذا خارج سيطرة التطبيق.
- عند حجب يوتيوب للعميل الافتراضي، يحاول التطبيق مرة ثانية بعميل بديل، ويظهر سبب يوتيوب الحقيقي في سجلّ فشل المهمة للمطوّر.
- روابط الصفحات العادية (مقالات، درايف بلا رابط مباشر) تُرفض برسالة واضحة؛ المطلوب رابط ملف صوت/فيديو مباشر أو يوتيوب.

## المصادقة

- صفحة التفريغ تُفتح من داخل بوت تيليجرام فقط، وترسل ترويسة `X-Telegram-Init-Data`.
- الخادم يتحقق من توقيع Telegram ويستخرج رقم المستخدم منه، ولا يعتمد على أي رقم يُرسل في النموذج.
- `/status` و`/download` و`/refine` تعمل لصاحب المهمة فقط.
- واجهة الورّاق تتحقق من `initData` بنفس الطريقة.

## التدقيق التلقائي

بعد كل تفريغ يصل الملف الخام فوراً، ثم يبدأ التدقيق تلقائياً وينتج نسختين إضافيتين تُحفظان في قاعدة البيانات، وتصلك رسالة بأزرار لتنزيلهما بصيغة TXT أو DOCX عند الحاجة:

- `<الاسم>_med`: نسخة مصححة إملائياً دون تغيير الكلمات.
- `<الاسم>_well`: نسخة محسّنة للقراءة مع فقرات وعناوين.

إذا رفض المزوّد النص لطوله يُقسَّم تلقائياً ويعاد، وإذا تعذر تدقيق جزء يُرسل تنبيه واضح مع إعادة النص الأصلي لذلك الجزء.

التدقيق يعمل على عدة قطع بالتوازي لتقصير الوقت، مع الحفاظ على ترتيب النص. ويوجد فحص تلقائي يمنع تغيير الأرقام أو إضافة أسماء إنجليزية أو حروف فارسية غير موجودة في الأصل. أما الشعر فيُعامل بمسار خاص يحافظ على الألفاظ وترتيب الشطرين بدل إعادة الصياغة.

## سرعة التفريغ الصوتي

- الملفات المدعومة وحجمها 24MB أو أقل تُرسل إلى Cohere مباشرة دون تحويل أو تقطيع.
- ملفات MP3 الكبيرة تُقطَّع بنسخ الضغط دون إعادة ترميز، وهي أسرع بكثير من إعادة الترميز الكامل.
- إعادة الترميز إلى MP3 أحادي 16kHz/24kbps تُستخدم فقط عند الحاجة (مثل m4a أو الصيغ غير المدعومة أو فشل النسخ).
- هذا يقلل زمن تجهيز الصوت قبل بدء التفريغ، خصوصاً في الملفات الطويلة.

## ملاحظات التشغيل

- نتائج التفريغ تُرسل إلى محادثة المستخدم في تيليجرام، والملف المؤقت في `/tmp` للتنزيل فقط.
- رسالة الحالة تتطور في مكانها: استلام → تنزيل → تفريغ، ثم تُحذف عند وصول النتيجة. لا تتراكم رسائل لكل مرحلة.
- عند إعادة تشغيل الخدمة تُعلَّم المهام غير المكتملة كفاشلة، وتُحذف مجلدات العمل القديمة.
- لا توجد حدود على حجم الملف أو عدد الطلبات؛ حدود تيليجرام/Render نفسها تبقى مطبقة.

## الفريق والمساهمون

- الفكرة والتطوير والاختبار الميداني: المطوّر البشري (`DEVELOPER_NAME`).
- المساهمة التقنية: عدة نماذج لغوية ساعدت في التصميم والكتابة والمراجعة والاختبار (`CONTRIBUTORS`).
- للتواصل والملاحظات: `/contact` داخل البوت. يكتب المستخدم الشروط ثم رسالته، فتُمرَّر إلى `DEVELOPER_CHAT_ID` مع اسمه ورابط حسابه، ويستطيع المطوّر الردّ على الرسالة نفسها فيصل الردّ للمستخدم. لا تُنشر بيانات المطوّر الشخصية.
- `/stats` للمطوّر وحده: عدد المهام اليوم والأسبوع، نسبة الفشل وأسبابها، متوسط زمن التفريغ، حالة الطابور، توزيع المحركات، وعدد التفريغات والمستخدمين.
- `/users` للمطوّر وحده: آخر 20 مستخدماً مع `@username` والاسم و`ID`، ويستعيد الأسماء القديمة من تليجرام ويحفظها. من حظر البوت أو حذف حسابه قد يظهر «بلا اسم مستخدم».
- `/allusers` للمطوّر وحده: كل مستخدم استخدم البوت منذ التأسيس (الأقدم أولًا)، مع أول استخدام وعدد المهام، مقسّمًا على رسائل إن طال.
- `/block <id>` و`/unblock <id>` و`/blocked` للمطوّر وحده: الحجب محفوظ في قاعدة البيانات (`blocked_users`)؛ المحجوب لا يستطيع رفع ملفات أو إرسال روابط أو مراسلة المطوّر، وتظهر له رسالة إيقاف مرة كل 30 دقيقة بدل التجاهل الصامت.
- `/msg <id> <نص>` للمطوّر وحده: مراسلة أي مستخدم دون أن يراسله أولًا؛ `/msg <id>` فقط يجعل «الرسالة التالية» هي المراد إرسالها. ردّ المستخدم على رسالة البوت يوجَّه للمطوّر تلقائيًا بنفس آلية `/contact`.
- التغذية الراجعة: بعد اكتمال التدقيق يظهر للعميل أزرار (ممتاز/جيد/يحتاج تحسين/ملاحظة). التقييم يُخزَّن في جدول `feedback` ويُمرَّر للمطوّر مع هوية المستخدم، وتقييم واحد لكل مهمة.
- قائمة الأوامر بعد علامة `/`: تُسجَّل عبر `setMyCommands` عند كل إقلاع، بقائمة عامة للجميع وقائمة خاصة بمحادثة المطوّر تتضمن أوامر الإدارة.
- كل رسالة في قناة السجل — نجاحاً أو فشلاً أو أرشفة — تعرض الآن اسم المستخدم واسمه الظاهر مع `ID`، بدل المعرّف وحده.
